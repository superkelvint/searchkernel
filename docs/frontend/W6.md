# W6 — Integration & Application Launch

## Status

The selected-index Integrations workspace now consumes the landed InstantSearch
authority from `integrations/instantsearch`. W6 no longer treats the adapter,
compatibility matrix, React/Vue qualification, or bounded public Search Endpoint
as unavailable.

Implemented:

- selected-index Integrations → InstantSearch.js route;
- live generation-bound validation of the selected admin target;
- direct consumption of the authoritative
  `integrations/instantsearch/src/compatibility.json` declaration;
- exact Vanilla, React and Vue install commands derived from the pinned package
  versions and adapter package version;
- generated Vanilla, React and Vue examples populated from an explicitly supplied
  public Search Endpoint URL and alias;
- a live preview that executes the real
  `createSearchKernelInstantSearchClient` adapter against that public endpoint;
- explicit presentation of supported widget/framework constraints;
- clipboard success/failure and stale selected-incarnation behavior.

The dashboard does not implement InstantSearch request/response translation,
widget semantics or a second compatibility matrix. Vite is allowed to read only
the canonical `integrations/instantsearch` package outside the dashboard root so
the dashboard build/tests consume the same source and declaration as the shipped
adapter.

## What remains unavailable

W6 is still not complete because the daemon has no dashboard management API for
public endpoint discovery/configuration.

The landed Search Endpoint is configured at deployment with
`--public-search-config` and `--public-search-listen`. W6 therefore cannot
authoritatively discover which public aliases exist, create/update/delete them,
inspect an endpoint configuration revision, or prove that a manually supplied
alias is bound to the selected admin target.

The workspace consequently accepts an explicit public `.../search` URL and
public alias for preview/code generation. Those values are session-only input,
not canonical endpoint state. A successful preview proves the supplied public
alias executes through the real adapter and public listener. It does **not** prove
that the alias maps to the selected logical index/generation.

A second backend issue also remains: public endpoint configuration currently
carries the registry generation token. Registry generations identify loaded
process incarnations and change on normal restart/reopen as well as
delete/recreate. A durable application binding must survive an ordinary restart
without silently adopting a deleted/recreated index. W6 must consume that
backend-owned identity once it exists rather than reconnecting by name.

## Ownership

W6 owns:

- integration UX;
- endpoint discovery/configuration UX once canonical APIs exist;
- generated application setup;
- compatibility presentation;
- live preview.

The InstantSearch compatibility track owns:

- request and response translation;
- pinned package/profile semantics;
- widget/framework compatibility;
- protocol correctness and executable qualification.

`searchkerneld` owns:

- bounded public Search Endpoint serving;
- listener/origin enforcement;
- exposure allowlists and policy;
- public alias → canonical target binding;
- durable endpoint identity and configuration state.

The dashboard never exposes trusted administration as application search and
never broadens listener/origin policy to make preview work.

## Verification

Use:

```sh
./dev test frontend
./dev test frontend-real-engine
./dev test instantsearch-compat
```

The frontend unit lane checks that W6 invokes the real adapter boundary, derives
installation/example data from canonical declarations, rejects admin-shaped
preview URLs and preserves public endpoint error codes. The browser lane covers
selected-incarnation behavior and W6 presentation against a real daemon.
`instantsearch-compat` remains the executable authority for the pinned
InstantSearch/React/Vue compatibility profile.
