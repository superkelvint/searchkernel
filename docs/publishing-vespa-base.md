# Publish and roll out the immutable Vespa base

This is the repeatable operator procedure for publishing Search Kernel's pinned
Vespa native base to GitHub Releases and then updating the self-hosted GitHub
Actions runners to consume it.

The canonical implementation is:

- `tools/package-native-base-artifact.sh`
- `.github/workflows/publish-native-base.yml`
- `tools/install-native-base-artifact.sh`
- `tools/resolve-native-sdk.sh`

The published base is immutable. Its compatibility identity is:

```text
build environment + native target + pinned Vespa commit
```

Do not overwrite an existing compatibility tag, repoint a tag, copy an archive
into an Actions `_work` checkout, or use a generic "latest" release as the
native-base identity.

## 1. What is published

For each build environment, currently `host` and `ci`, the publisher emits:

```text
searchkernel-vespa-base-v1-<build-env>-<native-target>-<vespa-commit>.tar.gz
searchkernel-vespa-base-v1-<build-env>-<native-target>-<vespa-commit>.tar.gz.sha256
```

under the matching release tag:

```text
vespa-base-v1-<build-env>-<native-target>-<vespa-commit>
```

The archive contains the immutable Vespa runtime/base plus the header/config
toolchain needed to compile Search Kernel's local adapter:

```text
searchkernel-vespa-base/
  base/
  toolchain/
    upstream/vespa/
    vespa-deps/include/
    vespa-deps/lib64/
  manifest.json
```

It deliberately does **not** contain Search Kernel-owned adapter output such as
`libsearchkernel_vespa.so` or `include/searchkernel_vespa.h`.

## 2. Preferred publishing procedure

Start from current `main`. The canonical publisher is the
`Publish native Vespa base` workflow:

```bash
gh workflow run publish-native-base.yml \
  --repo superkelvint/searchkernel \
  --ref main
```

Watch or inspect the run:

```bash
gh run list \
  --repo superkelvint/searchkernel \
  --workflow publish-native-base.yml \
  --limit 5
```

The workflow publishes both compatibility environments serially:

```text
host
ci
```

The trusted publisher runner must already have a clean, configured standalone
Vespa checkout at the exact commit pinned in
`core/native/vespa/manifest.json`.

The configured checkout must contain:

```text
searchcore/src/tests/proton/documentdb/CMakeFiles/searchcore_embedded_crud_spike_app.dir/flags.make
searchcore/src/tests/proton/documentdb/CMakeFiles/searchcore_embedded_crud_spike_app.dir/link.txt
```

The workflow refuses to publish from a dirty Vespa checkout or from the wrong
revision.

## 3. Exact manual equivalent

Use this when reproducing or debugging the publisher itself. Normal publication
should use the workflow above.

Update the repository:

```bash
git switch main
git pull --ff-only
```

Read the compatibility identity:

```bash
VESPA_COMMIT="$(python3 - <<'PY'
import json
with open("core/native/vespa/manifest.json", encoding="utf-8") as stream:
    print(json.load(stream)["vespa_commit"])
PY
)"
TARGET="$(rustc -vV | sed -n 's/^host: //p')"

printf 'Vespa commit: %s\nTarget: %s\n' "$VESPA_COMMIT" "$TARGET"
```

Verify the standalone Vespa checkout:

```bash
test "$(git -C upstream/vespa rev-parse HEAD)" = "$VESPA_COMMIT"
git -C upstream/vespa diff --quiet --ignore-submodules --
git -C upstream/vespa diff --cached --quiet --ignore-submodules --

test -f upstream/vespa/searchcore/src/tests/proton/documentdb/CMakeFiles/searchcore_embedded_crud_spike_app.dir/flags.make
test -f upstream/vespa/searchcore/src/tests/proton/documentdb/CMakeFiles/searchcore_embedded_crud_spike_app.dir/link.txt
```

### Publish the host artifact

```bash
export SEARCHKERNEL_BUILD_ENV=host

SK_NATIVE_DISABLE_PUBLISHED_BASE=1 ./dev native-sdk ensure

OUT="$PWD/target/native-base-artifacts/$SEARCHKERNEL_BUILD_ENV"
mkdir -p "$OUT"

mapfile -t FILES < <(
  bash tools/package-native-base-artifact.sh "$OUT"
)

ARCHIVE="${FILES[0]}"
CHECKSUM="${FILES[1]}"
TAG="vespa-base-v1-${SEARCHKERNEL_BUILD_ENV}-${TARGET}-${VESPA_COMMIT}"

if gh release view "$TAG" --repo superkelvint/searchkernel >/dev/null 2>&1; then
  echo "immutable release already exists: $TAG" >&2
  exit 1
fi

gh release create "$TAG" "$ARCHIVE" "$CHECKSUM" \
  --repo superkelvint/searchkernel \
  --title "SearchKernel immutable Vespa base $TAG" \
  --notes "Generated by the canonical pinned-Vespa publisher."
```

### Publish the CI artifact

Repeat the same sequence with:

```bash
export SEARCHKERNEL_BUILD_ENV=ci
```

The resulting tag is:

```text
vespa-base-v1-ci-<native-target>-<vespa-commit>
```

Do not delete or replace an existing release to force new bytes under the same
identity. If the actual compatibility inputs changed, update the corresponding
identity first.

## 4. What the packager guarantees

`tools/package-native-base-artifact.sh`:

1. resolves the canonical local Vespa base;
2. requires a standalone clean Vespa Git checkout;
3. requires `HEAD == manifest.json:vespa_commit`;
4. copies the immutable Vespa runtime/base;
5. packages Vespa source/header and generated header/config metadata required by
   the adapter build;
6. packages dependency headers;
7. rewrites producer-machine absolute paths in `flags.make` and `link.txt`
   to the canonical relocatable placeholders;
8. writes bundle/toolchain metadata containing build environment, target, and
   Vespa commit;
9. creates a deterministic tarball; and
10. writes a SHA-256 sidecar.

The deterministic archive is created with the equivalent of:

```bash
tar --sort=name \
    --mtime='UTC 1970-01-01' \
    --owner=0 --group=0 --numeric-owner \
    -czf "$ARCHIVE" \
    searchkernel-vespa-base

sha256sum "$ARCHIVE" > "$ARCHIVE.sha256"
```

## 5. Verify the GitHub Releases

List the exact release assets:

```bash
for BUILD_ENV in host ci; do
  TAG="vespa-base-v1-${BUILD_ENV}-${TARGET}-${VESPA_COMMIT}"
  echo "== $TAG =="
  gh release view "$TAG" \
    --repo superkelvint/searchkernel \
    --json tagName,assets
done
```

For the currently pinned x86_64 Linux base this should expose one
`.tar.gz` and one matching `.tar.gz.sha256` for each environment.

## 6. Roll the new base out to every Actions runner

Publishing the release is only half of the operation. Every self-hosted runner
that executes native CI must then provision the released **`ci`** base into
its persistent machine cache.

Do this as the same OS user that runs the GitHub Actions service. Do **not** run
it from a job checkout under `_work`.

The resolver installs into:

```text
${XDG_CACHE_HOME:-$HOME/.cache}/searchkernel/native-sdk-cache/
  ci/<native-target>/objects/<vespa-commit>/
```

A new pinned Vespa commit therefore installs beside the previous immutable
object. Do not manually delete the old object as part of routine rollout.

### Existing runner with a persistent Search Kernel provisioning checkout

If the runner has a durable Search Kernel checkout outside `_work`, update it
to current `main` and provision the CI namespace:

```bash
cd /path/to/persistent/searchkernel-provisioning
git fetch origin
git checkout -f origin/main

source "$HOME/.cargo/env"
SEARCHKERNEL_BUILD_ENV=ci ./dev native-sdk ensure
SEARCHKERNEL_BUILD_ENV=ci ./dev native-sdk path
SEARCHKERNEL_BUILD_ENV=ci ./dev doctor
```

If the runner bootstrap layout from `tools/ci/runner-bootstrap` is in use, the
default persistent checkout is:

```text
/opt/searchkernel/provisioning
```

and the persistent cache root is:

```text
/var/cache/searchkernel
```

Run the commands as the configured runner service account, not as root, so the
installed cache has the same ownership as later Actions jobs. With the default
runner-bootstrap layout, preserve the same cache environment used by the
service:

```bash
RUNNER_USER=actions-runner
RUNNER_USER_HOME="$(getent passwd "$RUNNER_USER" | cut -d: -f6)"

sudo -u "$RUNNER_USER" -H env \
  HOME="$RUNNER_USER_HOME" \
  XDG_CACHE_HOME=/var/cache/searchkernel \
  SEARCHKERNEL_BUILD_ENV=ci \
  bash -lc '
    source "$HOME/.cargo/env"
    cd /opt/searchkernel/provisioning
    git fetch origin
    git checkout -f origin/main
    ./dev native-sdk ensure
    ./dev native-sdk path
    ./dev doctor
  '
```

### Existing runner without a persistent Search Kernel checkout

This is the standalone procedure previously used for runners installed under
`/home/kelvin/actions-runner`. Keep the bootstrap script in the persistent
runner directory, **not** in `_work`.

Create `/home/kelvin/actions-runner/bootstrap-searchkernel-native.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

REPO="${SEARCHKERNEL_REPO:-superkelvint/searchkernel}"
REF="${SEARCHKERNEL_REF:-main}"
BUILD_ENV="${SEARCHKERNEL_BUILD_ENV:-ci}"

TOKEN="${GITHUB_TOKEN:-${GH_TOKEN:-}}"
if [[ -z "$TOKEN" ]] && command -v gh >/dev/null 2>&1; then
  TOKEN="$(gh auth token)"
fi
if [[ -z "$TOKEN" ]]; then
  echo "GITHUB_TOKEN/GH_TOKEN is unset and 'gh auth token' is unavailable" >&2
  exit 1
fi
export GH_TOKEN="$TOKEN"

TMP="$(mktemp -d)"
trap 'rm -rf "$TMP"' EXIT

fetch_repo_file() {
  local path=$1
  mkdir -p "$TMP/$(dirname "$path")"
  curl -fsSL \
    -H "Authorization: Bearer $TOKEN" \
    -H "Accept: application/vnd.github.raw+json" \
    "https://api.github.com/repos/$REPO/contents/$path?ref=$REF" \
    -o "$TMP/$path"
}

fetch_repo_file tools/resolve-native-sdk.sh
fetch_repo_file tools/install-native-base-artifact.sh
fetch_repo_file core/native/vespa/manifest.json

if [[ -f "$HOME/.cargo/env" ]]; then
  source "$HOME/.cargo/env"
fi

echo "Provisioning SearchKernel native base for $BUILD_ENV"
SDK_PATH="$(
  SEARCHKERNEL_BUILD_ENV="$BUILD_ENV" \
    bash "$TMP/tools/resolve-native-sdk.sh" ensure
)"

echo "Installed native base:"
echo "  $SDK_PATH"
echo "Persistent cache:"
echo "  ${XDG_CACHE_HOME:-$HOME/.cache}/searchkernel/native-sdk-cache"
```

Make it executable and run it as the Actions service user:

```bash
cd /home/kelvin/actions-runner
chmod +x bootstrap-searchkernel-native.sh
./bootstrap-searchkernel-native.sh
```

The script fetches only the current resolver, installer, and native manifest
from `main`; the resolver then downloads the exact GitHub Release asset for:

```text
ci + current Rust native target + current pinned Vespa commit
```

The release download is authenticated with `GITHUB_TOKEN`/`GH_TOKEN`, or the
token returned by `gh auth token`.

### Repeat on every native Actions runner

Do not assume provisioning one runner updates the others. Repeat the CI
`ensure` on each physical/VM runner because the native cache is machine-local.

After provisioning each runner, verify:

```bash
SEARCHKERNEL_BUILD_ENV=ci ./dev native-sdk path
SEARCHKERNEL_BUILD_ENV=ci ./dev doctor
```

or, for the standalone bootstrap, confirm that the printed SDK path is under the
persistent `ci/<target>/objects/<vespa-commit>` cache namespace.

## 7. End-to-end rollout checklist

Use this order whenever the pinned Vespa base changes:

```text
1. Update the pinned Vespa/native-base inputs on main.
2. Publish both host and ci immutable release assets.
3. Verify both release tags contain archive + SHA-256 sidecar.
4. On every self-hosted native Actions runner, update the provisioning view of main.
5. As the runner service user, run SEARCHKERNEL_BUILD_ENV=ci ./dev native-sdk ensure.
6. Verify SEARCHKERNEL_BUILD_ENV=ci ./dev native-sdk path.
7. Run SEARCHKERNEL_BUILD_ENV=ci ./dev doctor.
8. Only then rely on the runner for native CI.
```

The runner should never need to rebuild Vespa merely because a fresh Actions
job started. Once the released base is installed in the machine cache, worktrees
and independent clones on that runner reuse it read-only.
