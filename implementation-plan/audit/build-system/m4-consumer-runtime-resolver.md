# M4 consumer runtime resolver contract

Issue #942 implements the shared acquisition/cache contract used by later pip, npm, RubyGems, and Cargo integration work. It deliberately does not make any ecosystem package own a second cache algorithm.

The immutable key is the derived `runtime_identity` emitted by the qualified consumer-runtime artifact. Implementations must recompute `skrt-v1-<sha256>` from the canonical identity material before using it as a cache key. The default cache is `$XDG_CACHE_HOME/searchkernel/runtime` (or `~/.cache/searchkernel/runtime`), overridable with `SEARCHKERNEL_RUNTIME_CACHE`. Objects publish at `objects/<runtime_identity>` only after archive checksum, manifest identity, required-member, executable-mode, symlink-containment, and payload checksum validation. A per-identity advisory lock serializes cold acquisition and publication; staging is on the same filesystem and publication is an atomic rename.

Platform and artifact-origin selection are part of the machine-readable contract, not ecosystem-specific policy. The v1 qualified host is Linux x86-64 glibc with native target `x86_64-unknown-linux-gnu`. A descriptor for any other host fails before acquisition. The descriptor must name the exact immutable artifact `searchkernel-runtime-<runtime_identity>-<platform>.tar.gz`, use a permitted origin scheme, and carry the exact archive SHA-256. `SEARCHKERNEL_RUNTIME_ORIGIN` may replace only the origin/base during qualification or mirroring; the immutable filename and checksum remain fixed. Mutable "latest" selection is not a resolver concept.

`SEARCHKERNEL_RUNTIME_DIR` is the deployment/offline escape hatch. It bypasses acquisition only after the exact same manifest/ABI/payload validation. `prefetch` and `ensure` intentionally execute the same resolution path. `--offline` permits only a validated cache hit. A corrupt cache entry is never accepted; under the identity lock any file, symlink, or directory at the immutable object path is removed and reacquired, while an offline corrupt entry fails closed. Filesystem failures are reported through the stable `cache-io-failed` error code rather than leaking raw exceptions.

The machine-readable contract and executable language-neutral cache-key vectors live in `build/consumer-runtime/contract.json` and `build/consumer-runtime/conformance.json`. The resolver test consumes those vectors directly, so later Python, Node, and Ruby implementations have a mechanical identity/cache-key oracle rather than a prose convention. Ecosystem implementations must consume those semantics rather than infer repository paths, native-base locations, developer images, or ambient `LD_LIBRARY_PATH`.
