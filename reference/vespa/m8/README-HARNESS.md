# M8 verifier harness

M8 freezes the ordinary **local** Vespa request/result path. It is cumulative on M7 and deliberately does not add distributed dispatch or result merging.

## Files

```text
CONTRACT.md                 normative M8 behavior and non-goals
SOURCE_TRACE.md             pinned Vespa source areas to inspect
scenarios/*.json            frozen positive/negative scenario specification
oracle/ORACLE_SPEC.md       exact behavior the independent C++ oracle must perform
oracle/AUTHOR_ORACLE.md     authoring checklist for the oracle translation unit
oracle/build-cpp-oracle.sh  builds a reviewed direct C++ oracle against pinned Vespa
oracle/run-cpp-oracle.sh    runs only a provenance-checked oracle binary
expected/*.json             oracle-derived goldens; absent until authoring is complete
core/crates/searchkernel-vespa-engine/examples/  implementation-side Cargo targets
validate_scenarios.py       guards the scenario traps
validate_expected.py        guards canonical golden shape
compare.py                  exact canonical result comparison
check-structure.sh          defense-in-depth anti-shortcut checks
freeze-goldens.sh           runs reviewed oracle; never compiles it
freeze-immutable.sh         freezes the complete verifier after goldens exist
check-immutable.sh          implementation-time immutability check
verify-m8.sh                cumulative acceptance command
```

The public API is frozen by `core/crates/searchkernel-vespa-engine/examples/api-contract-m8.rs`.

## Authoring order

Do not hand M8 to an implementation agent until all steps below are complete.

1. Review `CONTRACT.md`, `m8.rs`, and every scenario.
2. Prepare verifier-owned local engine configuration fixtures for the scenario schema(s). These may be frozen from the already-green M6 configuration path or from the pinned Vespa config-model, but they must be checked in and must not be regenerated by the M8 implementation.
3. Author `oracle/m8_local_oracle.cpp` against the exact pinned Vespa checkout. Reuse the M4 `DocumentDB`/`PersistenceEngine` harness rather than inventing a new execution path.
4. For the text scenarios, consume the explicit frozen analysis annotations in the scenario. The C++ oracle must not tokenize/stem text. Review those annotations against M3 before freezing.
5. Build the oracle explicitly:

   ```bash
   ./reference/vespa/m8/oracle/build-cpp-oracle.sh
   ```

6. Review the direct oracle source and its provenance.
7. Freeze direct-C++ outputs:

   ```bash
   ./reference/vespa/m8/freeze-goldens.sh
   ```

8. Manually inspect all nine goldens, especially hit order, exact score bits, total hit count, the stored-text docsum case, and the composite term/range case.
9. Freeze the verifier:

   ```bash
   ./reference/vespa/m8/freeze-immutable.sh
   ```

After that, implementation acceptance is only:

```bash
./reference/vespa/m8/verify-m8.sh
```

## Critical traps

The scenarios are intentionally not interchangeable smoke tests:

- `limit-offset-sort-summary`: catches sorting/pagination performed after retrieval in Rust;
- `range-filter-pagination`: composes the real M7 filter path with M8 controls;
- `limit-zero-total`: catches `total_hit_count = hits.len()`;
- `offset-past-end`: catches totals accidentally reduced by pagination;
- `bm25-score-default-summary`: transports real native scores;
- `stored-text-selected-summary`: requires local docsums for a non-attribute text field;
- `multi-key-sort`: proves ordered native sort keys.
- `composite-term-range-pagination`: carries M7 boolean lowering through text matching, numeric filtering, sorting, and limiting.

## Frozen design choices

M8 does not extend the M7 YQL grammar with `ORDER BY`, `LIMIT`, projection, or summaries. A caller may use `Query::from_yql()` for the already-frozen M7 subset and then place the resulting `Query` in `SearchRequest`; request controls remain typed M8 fields.

M8 supports sorting on Integer attributes only. String/Float sorting is intentionally deferred to M9.
