# M8 direct C++ oracle specification

## Independence

The M8 oracle is a standalone direct Vespa C++ executable. It must not include or link:

```text
core/crates/searchkernel-vespa-engine
core/crates/searchkernel-vespa-bindings
core/native/vespa/searchkernel_vespa.*
```

It may reuse the lifecycle approach from the frozen M4 direct C++ oracle and its configured Vespa build artifacts.

## Pinned revision

Use exactly the commit in:

```text
reference/vespa/PINNED_VESPA.json
```

`build-cpp-oracle.sh` records:

```text
vespa_commit
oracle_sha256
binary_sha256
```

`run-cpp-oracle.sh` verifies all three before execution.

## Input

One positive scenario JSON path is supplied as argv[1].

The executable may use a small verifier-owned JSON reader or a mechanically generated line protocol. It must not use Search Kernel production parsing code.

The two M8 Text scenarios carry an explicit verifier-owned `analysis` array beside each raw Text fixture and query. These annotations are frozen inputs, not produced by the M8 implementation. They deliberately use only tiny cases already covered by M3/M4.

The direct C++ oracle must consume those exact term/span annotations using the same real `StringFieldValue` + linguistics span-tree mechanism established by M4. The M8 C++ code must not tokenize/stem text itself.

The Rust driver ignores the fixture `analysis` arrays and passes only raw text/query text through normal production M3/M7 behavior. This makes the M8 oracle independent of the Rust analyzer while avoiding a Java runtime dependency in every M8 verification run.

## Real engine setup

Use the same single-node embedded lifecycle proven in M4:

```text
DocumentDB
PersistenceHandlerProxy
PersistenceEngine
in-process transaction log
real config files
```

The config fixture may be generated by the M6 compiler for the Rust path, but the direct oracle must use semantically equivalent frozen configs independent of the implementation under test.

`run-cpp-oracle.sh` supplies `M8_ORACLE_FIXTURE_ROOT`, pointing at the verifier-owned `fixture/` directory. The oracle selects `attribute/` or `text/` from the frozen scenario family; it must not read production-generated config.

## Integer document setup

For M8 integer-only scenarios, insert/update real Vespa integer attribute documents. The multi-key-sort scenario contains two integer attributes; both must exist in the actual Vespa Document before matching.

## Text document setup

Use real `StringFieldValue` plus the M3 linguistic span/TERM annotation convention already established by M4.

For the stored-text scenarios the field is indexed and included in the default summary but is **not** an attribute.

## Query construction

Construct the required M7 query trees directly with Vespa query nodes. Do not invoke Search Kernel M7 code from the oracle.

Required scenario leaves are intentionally small:

```text
Term
Range
Exists
```

The oracle is allowed to share verifier-only helper code with M4 for query-tree construction.

## SearchRequest

For each scenario populate the real local request:

```text
request.queryTree / stack dump as required by pinned Matcher
request.ranking
request.maxhits = scenario.limit
request.offset  = scenario.offset
request.sortSpec = canonical Vespa sort specification
```

The sort spec for frozen cases must map mechanically:

```text
ascending  -> +field
descending -> -field
```

with keys concatenated in scenario order using the exact pinned sort-spec syntax.

## Match

Call the direct pinned local match entry point:

```text
DocumentDB::match(SearchRequest, ThreadBundle)
```

Record:

```text
SearchReply.totalHitCount
SearchReply.hits order
Hit::metric exact bits
hit GID/document identity
```

Resolve GID back to the fixture document ID using Vespa data structures in the oracle. Do not rely on scenario index position as the result identity.

## Docsums

If `summary == "none"`, do **not** call docsums.

Otherwise construct a real local `DocsumRequest`:

```text
resultClassName = "default"
hits = returned page's real GIDs/docids in hit order
```

For `{"fields":[...]}` call the pinned request field-list API.

Call:

```text
DocumentDB::getDocsums
```

Decode the returned Slime using the pinned response structure and return only the requested/default user summary fields. Strip transport metadata not exposed by the M8 Rust API.

The `stored-text-selected-summary` scenario is invalid unless the `title` value came from this real docsum path.

## Canonical output

Emit one JSON object:

```json
{
  "id": "scenario-id",
  "total_hit_count": 5,
  "hits": [
    {
      "document_id": "id:test:typea::...",
      "score_bits": "0x3ff0000000000000",
      "summary": {
        "qty": {"type":"integer","value":20},
        "title": {"type":"string","value":"..."}
      }
    }
  ]
}
```

Use lowercase fixed-width 16-digit IEEE-754 hexadecimal for scores/floats.

Hit order is not canonicalized by the verifier.

## Negative cases

Negative API validation cases are not oracle-generated. They are frozen contract errors checked against the Rust implementation because they describe the Search Kernel wrapper boundary, not an upstream engine result.

## Before freeze

The verifier author must manually inspect at least these oracle outputs before freezing:

```text
limit-offset-sort-summary
limit-zero-total
offset-past-end
bm25-score-default-summary
stored-text-selected-summary
multi-key-sort
```

This catches accidental `hits.size()` totals, post-pagination sorting, missing docsums, score stringification, and fixture-order identity bugs.
