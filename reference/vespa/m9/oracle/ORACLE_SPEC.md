# M9 direct C++ oracle specification

## Independence

The M9 oracle is a standalone direct pinned Vespa C++ program. It must not link or call Search Kernel Rust/native implementation code.

It may reuse the M8/M4 direct `DocumentDB` lifecycle helpers as verifier-owned source.

## Independent engine configuration

The oracle uses the frozen verifier-owned M9 attribute configuration described in `../fixture/README.md`. It must not call the production `ConfigCompiler` or consume configuration generated by the M9 Rust driver. The `attribute_price` profile is part of this verifier fixture.

`run-cpp-oracle.sh` supplies `M9_ORACLE_FIXTURE_ROOT`, pointing at that verifier-owned fixture directory. The oracle must load its config only from this path.

## Input and output

Input: one frozen M9 positive scenario JSON path.

Output: one canonical JSON object with one output step per scenario step, preserving step order.

```json
{
  "id": "scenario-id",
  "steps": [
    {"id":"before","op":"search", ...},
    {"id":"update","op":"update","ok":true},
    {"id":"groups","op":"group","result":{"key":null,"outputs":[],"groups":[...]}}
  ]
}
```

## Real multi-attribute documents

Build a real Vespa document type with the frozen M9 fixture attributes:

```text
category STRING attribute + summary
qty      INT32  attribute + summary
price    DOUBLE attribute + summary
active   BOOL   attribute + summary
```

Insert all scenario values into real Vespa Documents and feed them through the real persistence path.

For update steps construct real `DocumentUpdate` / assignment value updates and apply through the actual persistence/update path. Wait for/publication synchronization exactly as required by the pinned local engine before running the next step.

No verifier-side shadow map may be used to answer queries/grouping after the update.

## Query construction

Construct the direct pinned C++ equivalents of:

```text
AttributeEquals(String/Integer/Float/Boolean)
AttributeRange(Integer/Float; included/excluded/unbounded)
M7 Exists(Integer only)
```

Use the real query tree consumed by local Matcher.

The composite attribute-grouping scenario must build its conjunction through the same recursive query lowering as the leaf cases before passing it to the native grouping request.

For M7 `Exists`, retain the frozen Integer full-range representation. For Float presence, the M9 scenario uses `AttributeRange(Float, Unbounded, Unbounded)`. Do not synthesize generic String/Boolean existence semantics in the oracle.

## Search/sort

Search steps use the M8 local request/result rules.

M9 additionally exercises native sort specs over:

```text
String
Integer
Float
```

The oracle must not sort result vectors itself.

## Ranking fixture

Scenario `attribute-ranking-after-update` requires a frozen rank profile:

```text
name: attribute_price
first-phase: attribute(price)
```

This fixture is verifier-owned configuration. The direct oracle and implementation-under-test must receive semantically identical config.

Search before and after the price update through the real Matcher and record real hit score bits and order.

Do not calculate `score = price` in oracle post-processing. The expected score must come from `Hit::metric`.

## Native grouping request

For every `op=group` step:

1. compile the scenario Query to the direct local Vespa query tree;
2. set regular hit count to zero (`maxhits = 0`);
3. construct one local grouping level over the attribute classifier;
4. request native `count()` and any supported `average(attribute)` outputs;
5. preserve aggregation order from the scenario plan;
6. serialize the grouping request using the pinned Vespa object serialization used by `SearchRequest.groupSpec` (or use the pinned revision's direct equivalent);
7. run the request through `DocumentDB::match`;
8. deserialize `SearchReply.groupResult` with the matching pinned grouping classes;
9. read the actual native group keys/counts/aggregates.

The oracle must assert that the ordinary hit vector is empty for grouping scenarios. Group results must still be present.

## Constructing grouping objects

Prefer direct C++ construction using the pinned searchlib aggregation/expression classes.

The intended conceptual request is:

```text
group(attribute(classifier))
  each(output(count(), avg(attribute)))
```

The Rust Phase 7 model permits multiple recursive levels. The M9 legacy
positive corpus exercises one level; the dedicated recursive ABI verifier
exercises multiple levels. Sum, min, max, ordering, continuations, group hits,
and distributed merge are not supported variants.

If the pinned code makes group-spec serialization materially Java-owned and a direct C++ constructor would itself become a reimplementation, a verifier-only pinned Java helper may serialize the exact grouping object. If used:

- record the Java source trace;
- freeze its output bytes for each scenario;
- direct C++ still performs the actual local grouping execution;
- production may not use Java.

## Aggregate decoding

Native result mapping:

```text
count                    -> {"type":"integer","value":i64}
average                  -> {"type":"float","bits":"0x..."}
```

If the pinned engine returns an integer aggregate in a wider/different native wrapper, preserve the exact mathematical result so long as it fits frozen Rust `i64`; fail authoring if the pinned behavior cannot be represented losslessly.

Group keys map to `GroupingResultValue` JSON. M9 positive grouping cases use
String, Integer, and Float keys. Float values are emitted by their exact IEEE
754 bits. The root key is null and every node has ordered `outputs` and
recursive `groups` arrays.

## Canonical group order

The oracle may emit native group order. `compare.py` canonicalizes group arrays by typed key before comparison because M9 does not contract incidental group order.

Never canonicalize regular search hit order.

## Zero-hit anti-shortcut proof

The direct oracle must set `SearchRequest.maxhits = 0`, derive the ordinary hit count from the actual `SearchReply.hits.size()`, and fail the oracle run if it is non-zero. The ordinary hit count is an oracle assertion, not a fabricated field in the public Rust result.

The implementation-side structural check also requires the local grouping adapter to set the native request's regular hit count to zero and to use `groupSpec`/`groupResult`. Runtime scenario `string-facet-counts` contains more documents than the normal search page size, so a wrapper that groups only returned hits cannot pass.

## Update-sensitive cases

Manually inspect oracle outputs for:

```text
update-changes-filter-membership
attribute-ranking-after-update
grouping-after-update
```

The result after update must be produced by the same live engine instance so stale attribute vectors/publication bugs are visible.

## Negative cases

M9 negative cases freeze Search Kernel wrapper validation and are checked directly against the Rust API. The direct oracle is not used to define wrapper error category names.
